# Why SBOMs, Instead of Scanning the Dependency Cache Directly

This is the single most important design decision behind the SCA pipeline,
and the one with the most concrete evidence behind it. This page is the
canonical explanation; other pages link here instead of repeating it.

## The problem: scanning `~/.m2` directly produced 300+ false positives

Early local testing against `platform-backend` (a Maven, Spring Boot
project) scanned the raw local Maven repository (`~/.m2`, populated by
`mvn dependency:resolve`) instead of a generated SBOM. The result was
over 300 CVE findings, most of them false positives, with no realistic way
to patch or triage all of them individually.

## Why: how Maven's local repository actually works

`~/.m2/repository` is not just "the project's dependencies", it's a cache
of every artifact Maven has ever downloaded or built locally, including
transitive dependencies that were later overridden. Two files land in the
cache for every library Maven downloads: the JAR (the compiled code) and
the POM (that library's own declared dependency list, at whatever version
that library's authors originally specified).

A scanner pointed at `~/.m2` reads every POM file it finds and treats each
declared version as if it were actually used in the build, even when
Maven's own conflict resolution overrode that version somewhere else.

**Concrete example, encountered directly during testing:**

- The project depends on `micrometer-core 1.16.5`.
- Inside micrometer's own POM, it declares `tomcat-embed-core 8.5.100` as
  one of its dependencies. That's micrometer's declaration, not the
  project's.
- The project also declares `tomcat.version 11.0.22` directly.
- A scanner reading `~/.m2` sees the POM-declared `8.5.100` and flags it
  as vulnerable, a version the project never actually ships.
- Maven itself resolves the conflict at build time and picks `11.0.22`.
  `8.5.100` never ends up in the actual built application at all.

## How Maven resolves version conflicts

This false-positive pattern exists because of how Maven picks a single
winning version when multiple declarations conflict:

- **Nearest Definition:** Maven resolves version conflicts by picking the
  version "nearest" to the root of the dependency tree (a breadth-first
  traversal).
- **First-Come Wins:** if two dependencies share the same depth in the
  tree, the one declared first in the `<dependencies>` block wins.
- **BOM Order:** if multiple BOMs are imported in
  `<dependencyManagement>`, the first BOM to define a version for an
  artifact wins. Overriding a BOM-managed version manually requires
  declaring the desired version in the project's own
  `<dependencyManagement>` *before* importing the BOM that manages it.

None of this resolution logic is visible to a scanner reading raw POM
files in a cache. It only becomes visible in the artifact Maven produces
*after* resolution finishes.

## The fix: scan the SBOM, not the cache

An SBOM (Software Bill of Materials) generated by the CycloneDX plugin
(`org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom` for Maven,
`@cyclonedx/cyclonedx-npm` for npm) is built **after** Maven or npm
finishes all conflict resolution. Using the example above: the SBOM
contains only `tomcat-embed-core 11.0.22`, the version actually resolved
and used. `8.5.100` never appears in it. A scanner reading the SBOM
correctly sees no vulnerability for that dependency, because it's scanning
what the project actually ships, not every version that was ever declared
anywhere in the dependency graph.

For npm projects, the equivalent logic applies to `package-lock.json` and
the installed `node_modules/` tree: `cyclonedx-npm` walks the actual
installed tree, which only exists after `npm ci` runs against
`package-lock.json`. This is why the SBOM effectively reflects
`package-lock.json`, not the looser version ranges in `package.json`, and
why `npm ci` (not `npm install`) is required before SBOM generation, see
[pipeline-sca.md](../reference/pipeline-sca.md).

## Measured impact

Testing against `platform-backend` compared three different scan scopes
directly:

| Scan scope | Critical findings | Assessment |
|---|---|---|
| `mvn dependency:resolve` only, scoped to project deps | 46 | Correct scope |
| `mvn dependency:resolve-plugins` added | 113 | Maven build tooling, not runtime, false positives |
| Full `~/.m2/repository` cache | 91 | Too broad, includes unrelated libraries never used by this project |

The SBOM-based approach is what the SCA pipeline uses in production, it
corresponds to the first row.

## Secondary benefit: tool stability

Scanning a cache directly, rather than a resolved SBOM, also creates a
second class of problem unrelated to false positives: for artifacts not
already present locally, some tools attempt to fetch metadata live from
the upstream registry (for example, Trivy resolving against Maven
Central). Under repeated CI runs from the same IP range, this can trigger
registry-side rate limiting (HTTP 429), which fails the tool run entirely,
not just the scan quality. Scanning a pre-generated SBOM avoids this class
of failure for the scan step itself. See
[troubleshoot-maven-rate-limit.md](../how-to/troubleshoot-maven-rate-limit.md).

## What an SBOM is, briefly

An SBOM is a list of every software component and dependency in a
project, the equivalent of an ingredients list for software.
[CycloneDX](https://cyclonedx.org/) is the standard format used here, a
structured schema (JSON in this setup) for representing that inventory
consistently so tools like Trivy and OSV-Scanner can parse it reliably.
